Project plan and troubleshooting blog

How StudyFlow was planned over three one-week sprints, which parts of the Agile methodology were adopted and why, and two errors that were hit and fixed along the way.

1. Why Agile, and which parts of it I used

The Agile Manifesto values working software over comprehensive documentation and responding to change over following a plan (Beck et al., 2001). For a three-week solo assignment that sounded like an excuse to skip planning, so I read it the other way round: keep the plan short, but make it something that can change without being rewritten.

Two constraints shaped the approach. First, the specification was fixed and would not move, so there was no customer to negotiate scope with — the "customer" was the marking rubric. Second, I was the only developer, which removes the coordination overhead Agile is usually designed to absorb. What remained useful were the parts about short iterations and frequent, working checkpoints.

Concretely, three aspects of Agile were adopted:

  • Timeboxed sprints with a shippable increment. Each week ended with a version of the site that could be opened in a browser and demonstrated, even if incomplete. Week 1 shipped the home page and the shared stylesheet; week 2 shipped the task manager; week 3 shipped the blog, the ethics page and the README. A page that renders badly but renders is a better checkpoint than a perfect page that exists only in a notebook.
  • Prioritised backlog, ordered by risk. The riskiest item was not the HTML — it was date handling and validation, which I had never written before. That went into sprint 2, early in the week, so that a failure would still leave time to simplify the design. Cosmetic work (image gallery styling, hover states) was deliberately last.
  • A retrospective at the end of each week. Ten minutes with the site open, asking three questions: what works, what is fragile, what will bite me next week. The first retrospective produced the decision to store dates as ISO strings, which is what prevented a whole class of bugs later (see error 1).

Aspects I deliberately did not adopt: daily stand-ups (nothing to synchronise with), story-point estimation (one person, one velocity — the numbers would be decoration), and pair programming. Agile is a set of practices to be chosen from, not a compliance checklist; the reason for each choice above is that it removed a specific risk in this project.

3. Troubleshooting log

Two errors are documented below, both from sprint 2. For each one: when it was found, what it looked like, the code that caused it, and how it was resolved.

Error 1 — A task due today was rejected as "in the past"

Date and time encountered: 8 November 2026, 09:14 (ACDT)

Symptom. Entering today's date in the due-date field produced The due date cannot be in the past and the form refused to submit. The same date was accepted after about 10:30 in the morning, which was the clue: the behaviour depended on the time of day, not on the date.

Code that caused the issue

// validation.js (before)
function validateDueDate(value) {
  if (value === '') return 'A due date is required.';

  var due = new Date(value);      // "2026-11-08"
  if (due < new Date()) {   // now
    return 'The due date cannot be in the past.';
  }
  return '';
}

Cause. A date-only string is parsed as UTC midnight, not local midnight. In Adelaide (UTC+10:30 during daylight saving) "2026-11-08" becomes 10:30 am local time. At 9:14 am, "today" therefore evaluated to a moment in the future, and the comparison due < now was false for the wrong reason — until the clock passed 10:30, at which point the same test started passing. The obvious fix — comparing Date objects — would still have been fragile, because a user in a negative UTC offset would see the date shift backwards instead.

Date and time resolved: 8 November 2026, 10:02 (ACDT)

Corrected solution

// Build a local calendar date as a sortable string.
function isoLocal(date) {
  var y = date.getFullYear();
  var m = String(date.getMonth() + 1).padStart(2, '0');
  var d = String(date.getDate()).padStart(2, '0');
  return y + '-' + m + '-' + d;
}

function validateDueDate(value) {
  if (value === '') return 'A due date is required.';
  if (!/^\d{4}-\d{2}-\d{2}$/.test(value)) return 'Enter a date in the form YYYY-MM-DD.';

  // String comparison of ISO dates is date-only and timezone-free.
  if (value < isoLocal(new Date())) {
    return 'The due date cannot be in the past.';
  }
  return '';
}

How it was resolved. Every date in the application is now stored as a YYYY-MM-DD string, and every comparison compares two such strings. Because the format is fixed-width and big-endian, lexicographic order equals chronological order, so no Date object and no timezone is involved in the decision. Date objects are created only for display and for the "days remaining" calculation, and those are constructed with an explicit T00:00:00 suffix so they stay in local time.

Resources used. MDN's Date.parse() reference (it documents that date-only forms are treated as UTC); ECMA-262 §21.4.3.2 on the Date Time String Format; a Stack Overflow thread on "JavaScript date is off by one day" that described the same symptom. The fix itself came from the first sprint retrospective rule: prefer plain sortable strings where a comparison does not need a clock.

Error 2 — Deleting several tasks in a row skipped one

Date and time encountered: 9 November 2026, 16:41 (ACDT)

Symptom. With four tasks in the table, clicking delete, confirming, then deleting the next one, left a task behind and deleted a different one than the dialog named. It only happened when two deletions followed each other quickly without a page reload.

Code that caused the issue

// tasks.js (before)
function deleteTask(id) {
  tasks.forEach(function (task, index) {
    if (task.id === id) {
      tasks.splice(index, 1);   // mutates the array being iterated
    }
  });
  render();
}

Cause. splice() mutates the array while forEach() is walking it. Every element after the removed one shifts down by one index, but the loop counter has already advanced, so the element that moved into the vacated slot is skipped. With a single deletion the skipped element is usually not the target, which is why the bug looked intermittent. It was not a rendering problem at all — the data itself was wrong — but the table redraw made it look like the view had gone out of sync.

Date and time resolved: 9 November 2026, 17:05 (ACDT)

Corrected solution

// tasks.js (after) — build a new array instead of editing in place.
function deleteTask(id) {
  tasks = tasks.filter(function (task) {
    return task.id !== id;
  });
  saveTasks();
  render();
}

How it was resolved. Deletion now produces a new array containing every task that is not the target, which cannot skip an element because nothing is being iterated while it changes. The same pattern was applied to the update path: the table is always rebuilt from the array (the single source of truth) rather than patched row by row, so the data and the screen cannot disagree.

Resources used. MDN documentation for Array.prototype.filter() and Array.prototype.splice() (the latter notes that it changes the array in place); the MDN guide "Array methods" section on avoiding mutation during iteration; and a Stack Overflow answer describing the skipped-element symptom when splicing inside forEach.

4. What I would do differently

  • Write the validation rules before the interface. Both errors above were logic errors, and both would have been caught by testing the functions with a fixed set of inputs before wiring them to a form.
  • Keep a decision log from day one. The timezone fix came from a rule recorded in a retrospective; the rules that were never written down were the ones that had to be rediscovered.
  • Commit smaller. The history for sprint 2 has three commits where there should have been fifteen, which made the second bug harder to bisect.
